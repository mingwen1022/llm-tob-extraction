Orchestrator 产品架构：多场景 toB 结构化抽取

一个入口，贴任意文档文本 → 自动识别文档类型（路由）→ 选对应领域专家 LoRA adapter → 抽取标准化 JSON。调用方不用指定文档类型，也不用维护多套入口。

1 个共享基座 + 3 个 LoRA adapter 路由准确率 98.9% Gradio 本地可跑 尚未公开部署（见 §4）

1. 架构

输入文档文本（OCR文本 / 网页正文 / 公告全文）
   │
   ▼
[ 路由：Qwen3.5-4B 零样本判类 ]  ← 零训练分类器，加新域不用重训
   │  domain ∈ {cord, duee_fin, ccks_fraud}
   ▼
[ 选对应 adapter + schema ]
   │
   ▼
[ 共享基座 Qwen3.5-4B（常驻，冻结）+ set_adapter(domain) ]
   │
   ▼
标准化 JSON 输出（按该域 schema 约束）

本质等价于 vLLM --enable-lora 多LoRA服务——这里用 HF PEFT 原生多 adapter 支持在本地跑通，验证整条链路。完整端到端精度/延迟数字见评测结果页 §3。实时可点的界面见产品Demo（需本地已启动服务，见 §4）。

2. 真实调用走查（非模拟数据，均为 test 集真实样本 + 模型真实输出）

2.1 票据抽取（CORD，英文）

# INPUT（OCR文本，注意原文本身就比较乱，这是真实OCR质量）
901016 -TICKET CP
2 60.000 60.000
TOTAL DISC $ -60.000
TAX 5.455
Subtotal 60.000
TOTAL (Qty 2.00 60.000
EDC CIMB NIAGA No: xx7730 60.000

# 路由结果 → cord
# 抽取输出（E2 真实输出，与 gold 完全一致）
{"menu": [{"nm": "-TICKET CP", "cnt": "2", "price": "60.000"}],
 "sub_total": {"subtotal_price": "60.000", "tax_price": "5.455"},
 "total": {"total_price": "60.000"}}

2.2 金融公告事件抽取（DuEE-fin，中文）

# INPUT（节选）
原标题：宇晶股份(25.050,0.78,3.21%)：持股 7.125%的股东拟减持不超过2%
宇晶股份晚间公告，持股 7.125%的股东深圳市珠峰基石股权投资合伙企业拟减持不超过200万股，即不超过公司总股本的2%。

# 路由结果 → duee_fin
# 抽取输出（E2 真实输出）
{"events": [{"event_type": "股东减持", "披露时间": "晚间", "股票简称": "宇晶股份",
             "减持方": "深圳市珠峰基石股权投资合伙企业",
             "交易股票_股份数量": "不超过200万",
             "减持部分占总股本比例": "不超过公司总股本的2%"}]}

诚实标注：最后一个字段 gold 是"不超过2%"，模型输出"不超过公司总股本的2%"——同一件事、措辞不同，字段级精确匹配会判为不命中。这是评测方法本身的已知局限（自由文本字段的表述多样性），详见评测指标页。

2.3 反欺诈案例要素抽取（CCKS，中文）

# INPUT
@支付宝 我姐昨天在支付宝被盗刷八千!!!申诉也是直接秒拒[微笑][微笑]@蚂蚁金服客户中心

# 路由结果 → ccks_fraud
# 抽取输出（E2 真实输出）
{"event_type": "盗用风险/信息未泄露/其他", "资损金额": "八千",
 "支付渠道": "支付宝", "受害人身份": "我姐"}

诚实标注：这条漏了"涉案平台"（gold="蚂蚁金服"）——CCKS 是三域里绝对分数最低的（噪声更大、字段更稀疏），这条真实漏抽正好体现了这一点，没有挑选"完美样本"来展示。

3. 为什么用本地 LoRA，而不是直接调大模型 API

方案CORD micro-F1DuEE-fin micro-F1边际成本数据出境可私有化
本地 4B LoRA（本demo）0.9450.861$0否✅
Gemini-3.5-Flash（前沿API）0.866—按量是❌
Qwen3.7-Max（国产大模型）0.854—按量·思考模式×5是部分
DeepSeek-V4-Pro（国产大模型）0.838—按量·思考模式×5是部分
基座·完整prompt（不微调）0.6470.322$0否✅

在数据不能出域的金融/票据场景，微调后的本地小模型在精度、成本、合规三个维度全面胜出——两个语言/任务完全不同的域，微调提升幅度几乎一致（+0.54）。完整选型对比见总览页。

4. 本地运行 & 部署状态

需要本地跑一个 Ollama 服务（qwen3.5:4b，供路由零样本判类用），再启动 Gradio：

# 首次或环境变过：infer + demo 两个 extra 必须一起装（分开装会互相覆盖依赖）
uv sync --extra infer --extra demo

# 启动
uv run python scripts/demo_app.py
# → 打开 http://127.0.0.1:7860

首次调用会冷加载基座 + 3 个 adapter，约 10-20 秒；之后每次抽取约 8-10 秒/条（Mac MPS，未做生产优化）。

当前仅本地运行，尚未公开部署
已知阻塞点：路由目前依赖本地 localhost:11434 的 Ollama 服务，云端容器（如 HF Spaces）里不存在——公开部署前需要把路由改成直接复用同一个已加载的 transformers 基座做零样本判类，去掉 Ollama 这个外部依赖。 HF Spaces 免费 CPU 档对 4B 模型推理太慢（不到能用的程度），真要公开访问需要 ZeroGPU（免费但有每日GPU时长配额）或付费 GPU（可设闲置自动休眠控制成本）。
