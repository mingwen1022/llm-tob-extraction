## 1. 先厘清一个容易混的点："测不同裸模型"有两种角色

截图讨论过，这里定死，别混：

| 角色 | 是什么 | 换不换 | 目的 |
|---|---|---|---|
| **① 微调用的共享基座** | 所有 adapter 冻结共用的那个底座 | **锁死**（Qwen3.5-4B，全程不换） | 保证 orchestrator 能一卡多 LoRA 热插拔 |
| **② 每个域的对照基线** | 每个域都跑一遍 base零样本/约束/你的LoRA/API | **每域重跑** | 得出该域"该用本地还是直接调 API"的结论 → 驱动路由 |

- **模型选型能力**体现在两处：**(a) 一次性的"共享基座 bake-off"**（选定 ① 该用哪个底座）+ **(b) 每域的 API-vs-本地对照**（②）。
- **绝不**每个域重新挑 fine-tune 基座——那会拆掉架构。基座 bake-off 只在一个代表域（CORD）做一次。

## 2. 分阶段计划

### Phase A · 补完 CORD 选型矩阵（P0，核心，全在 CORD 免费 gold 上）
这是"选型研究"成立的关键，**优先级最高、成本最低**。

1. **E4 前沿 API 基线**：GPT-4o + 一个国产（DeepSeek-V3 / Qwen-Max）在**同一 CORD test、同一评测器**上跑 → 选型关键轴。
2. **E1 / E3 约束解码**：Colab/GPU 上 vLLM `guided_json` 跑基座+LoRA 的约束版。
3. **加两列**：成本（$/1k 文档，API 计价 vs 本地摊薄）+ 延迟（s/文档）。
4. **写决策结论**：一张"精度×成本×延迟×合规"推荐表 + 一段"为什么本地 LoRA 是金融场景对的选择"。

> 产出：完整 E0–E4 矩阵。**这一步做完，选型研究就完整了**（不依赖多场景）。

### Phase B · 共享基座 bake-off（一次性，体现"训练基座选型"）
在 CORD 上，用**同一 LoRA 配方**训 2–3 个候选基座，选/确认共享底座：

- 候选：**Qwen3.5-4B**（现选）vs **Qwen2.5-7B** vs **Llama-3.2-3B**（或 Gemma-3-4B）
- 同 r=16、同数据、同评测 → 出一张"基座 × F1 × 显存 × 速度"表 → **给"为什么锁 Qwen3.5-4B"补量化证据**
- 产出：一次性结论，写进架构页。**别每域重做。**

### Phase C · 加第二个域：合同（让"多域"从口号变真）
选**合同/NDA**（最 toB、最 fintech）：

- 数据：**CUAD**（41 类合同条款，专家标注）或 **RealKIE-NDA**（3 字段，最省事）
- 流程：**先跑 `dedup_check`** → span 标注转 JSON → 训同基座 r=16 adapter → 跑该域 E0–E4 对照表
- 关键：复用 `shared/` 全部流水线，**只新写 `convert_<域>.py` + 注册 schema**

### Phase D · 加第三个域：发票（含行项，难度上一层）
- 数据：**DocILE**（6.7k 标注发票 + 55 字段 + 行项识别，需申请）或 **RealKIE-FCC 发票**（11 字段，直接可用）
- 同 Phase C 流程

### Phase E · 路由 + Orchestrator（产品的"中间模型"）
- **路由器（中间模型）**：输入文档 → 判类型 → 选 (adapter, schema)。三选一：
  - (a) 句向量 + 轻量分类器（快、可控、好评测）
  - (b) 基座零样本判类（省事）
  - (c) 元数据/规则（有先验时）
- **vLLM 多 LoRA 热插拔**：1 冻结基座 + N 域 adapter
- **端到端**：`文档 → 路由 → (adapter+schema) → 约束解码 → JSON`
- 指标：路由准确率（混淆矩阵）+ 各域 F1 + 端到端 F1（路由误差会传播，单独测）

### Phase F · 产品化 + 呈现
- **Gradio demo（这就是"产品"）**：上传任意文档 → **自动识别类型 → 路由到对应本地 adapter → 出 JSON**，并**实时显示"本地 LoRA vs GPT-4o API"的成本/合规对比**
- HF Space 部署 + HF Hub 上传 adapter + model card（写上分数）
- 公开 repo + 清理 README + 站点建产品详情页

## 4. 可用的 toB 公开数据集（都自带 gold，无需手搓）

| 场景 | 数据集 | 字段/特点 | 获取 | 就绪度 |
|---|---|---|---|---|
| **票据** | **CORD**（已用） | 小票，gt_parse 现成嵌套 JSON | HF 直接 | ⭐⭐⭐ 最易 |
| **合同** | **CUAD** | 510 合同，41 类条款，专家标注 | 公开直下 | ⭐⭐⭐ 最 toB |
| **合同/NDA** | **RealKIE-NDA** | 3 字段（生效日/管辖/签约方） | 官网申请 | ⭐⭐ 省事 |
| **发票** | **DocILE** | 6.7k 标注 + 55 字段 + 行项识别 | 申请表 | ⭐⭐ 最专业 |
| **发票** | **RealKIE-FCC** | 11 字段（含行项级） | 官网申请 | ⭐⭐ |
| **财报/招股** | **RealKIE-SEC S1** | 24 字段，金融 | 官网申请 | ⭐⭐ fintech |
| **长文档报告** | **Kleister**（NDA/Charity） | 人名/角色/日期/金额，长文档 | 公开 | ⭐⭐ |
| **表单** | **FUNSD / XFUND** | 表单 key-value，XFUND 多语(含中文) | 公开直下 | ⭐⭐ 结构不同 |
| **业务文档多任务** | **BuDDIE**(2025) / **KVP10k** | 业务文档 KV 抽取 | 公开 | ⭐ 较新 |

**推荐组合（fintech 味 + 都有 gold + 三种截然不同的文档）**：
> **CORD 票据（已做）+ CUAD 合同 + RealKIE-FCC 或 DocILE 发票** → 三个真正不同的域，路由才有意义。

> ⚠️ 措辞：CUAD/RealKIE/DocILE/FUNSD 多是 **span 级标注**，需写脚本转 JSON（这步本身是"数据工程"加分项）；只有 CORD 是现成 JSON。DocILE/RealKIE 需填申请表。
