# LLM-LoRA 项目 · 定位与方案（定稿 v2）

> 面向求职：中国国内 AI 产品经理（to-B / fintech 为主）
> 一句话定位：**面向本地私有化部署的 to-B 文档抽取——一个"用大模型 API 还是本地微调小模型"的模型选型 + 评测研究。**

---

## 0. 先纠正一个认知：这个项目考的不是"训得多难"

招 AI PM 的人看模型项目，要确认的是三件事，**都和训练耗时无关**：
1. **模型选型判断**：给定任务，选对、并说清为什么（模型↔任务↔成本↔延迟↔合规）
2. **评测能力**：定义指标、严谨验证"够不够上线"
3. **能跟工程对话**：微调 vs RAG vs prompt、约束解码、量化/serving 成本

所以这个项目的价值不来自"LoRA 训了多久"，来自**它把一个微调包装成了一个有对比、有取舍、有结论的选型决策**。"周末就跑完"不是缺点——只要外面包着选型逻辑 + 严谨评测 + 合规视角。

---

## 1. 定位

- **它在项目组合里补的缺口**：四大支柱（业务纵深 / 模型深度 / 工程交付 / 评测可靠）里的**"模型深度 + 有 gold 量化选型"**。其余项目都不占这块（emg 是从零搭 DL、不是 LLM 微调；流程 Agent 是"无 gold 生产评测"；CS263 是"别人给了干净 benchmark 的 agent 评测"）。
- **和其他评测项目不重复**（三种不同评测处境）：
  | 项目 | 评测处境 |
  |---|---|
  | CS263 | 别人给了干净 benchmark（Tau2 DB-state 客观） |
  | **本项目** | **公开数据自带 gold → 量化模型选型** |
  | 流程 Agent | 生产场景、没有现成 gold → 评测体系设计 |
- **为什么锚在公开数据集（CORD）**：离职后没有业务数据、手搓主观 gold 会踩 CS263 的效度坑。**公开 benchmark 白嫖 gold**，直接绕开数据问题。CORD 本身是文档 AI 领域半标准集（Naver Clova，论文常用），可信、可复现。
  - ⚠️ 措辞诚实：现在跑的是 **CORD 小票**数据集，写的时候说"方法在 CORD 验证，直接迁移到企业发票 / 合同 / 票据"，别把数据集直接叫"发票"。

## 2. 核心方案：把它做成一张"选型决策矩阵"

**Thesis（要证明的结论）**：在数据不能出域的 to-B 文档抽取场景，**微调后的本地小模型，在"精度 × 成本 × 延迟 × 合规"的帕累托前沿上，胜过纯 prompt 和前沿大模型 API。**

用你 README 里已经设计好的实验矩阵（E0–E4）跑完就成立——**这不是加难度，是把已规划的做完**：

| 编号 | 配置 | 状态 | 作用 |
|---|---|---|---|
| E0 | 基座·自由解码 | ✅ 已做（F1 0.409 / schema 26%） | 下限 |
| E1 | 基座·约束解码（vLLM guided_json） | ⬜ 待做 | "不训练的廉价修法"能到哪 |
| E2 | LoRA·自由解码 | ✅ 已做（F1 0.950 / schema 100%） | 你的赌注 |
| E3 | LoRA·约束解码 | ⬜ 待做 | 微调 + 约束的上限 |
| **E4** | **前沿 API：GPT-4o + 国产（DeepSeek-V3 / Qwen-Max）** | ⬜ 待做 | **选型关键轴——"直接调大模型行不行"** |
| E5（可选） | RAG / few-shot 基线 | ⬜ 可选 | 证明瓶颈是"行为"该用微调、不是"知识"该用 RAG |

跑完后，**加两列把它变成真正的决策**：**成本（$/1k 文档，API 计价 vs 本地摊薄）** 和 **延迟（s/文档）**。于是从"我微调了一下"变成"给定任务、四维权衡后的选型结论"。

**决策结论（预期长这样，用真实数字填）**：
> GPT-4o 精度高但数据要出境（金融合规红线）+ 按 token 计费；本地 4B LoRA 拿到 **0.95**、零边际成本、可私有化部署——**这才是金融场景对的选择**。约束解码作为不训练的兜底，把非法输出从 26% 拉到接近 100%。

## 3. 关键决策与工程发现（面试深度，已有）

这些你已经踩出来了，是"能跟工程对话"的直接证据，写进去：
- **微调 vs RAG vs prompt 的判断**：基座把金额输出成数字（type 错）导致 schema 合法率只有 26%——这是**"行为/格式"问题 → 该微调**，不是"知识"问题（RAG 解不了）。26%→100% 是教科书案例。
- **`think:false`**：Qwen3.5 默认思考模式在抽取前狂生成推理 token，关掉后 **79s → 2.17s（35×）**。
- **约束解码归到 vLLM**：Ollama/llama.cpp 对 qwen3.5 的 schema→GBNF 语法没接上（`format:<schema>` 被忽略，仍生成 `60-5.455+60` 非法表达式）→ E1/E3 改用 **vLLM `guided_json`（GPU）**，可靠、与架构无关。
- **自建评测器**：flatten → 多重集 → 字段级 P/R/F1（micro/macro/per-field）+ JSON 合法率——因为要字段级、要能诊断"幻影字段"（基座结构嵌套错位产生的 F1=0 字段，微调后 15→9 消失）。

## 4. 下一步做什么（优先级排序）

### P0 · 完成选型矩阵（核心，全在 CORD 免费 gold 上，一块 GPU / Colab 几天）
1. **E4 前沿基线**：GPT-4o + 一个国产（DeepSeek-V3 或 Qwen-Max）在**同一 CORD 测试集、同一评测器**上跑。← 最重要，这是选型的关键轴。
2. **E1 / E3 约束解码**：Colab/GPU 上用 vLLM `guided_json` 跑基座 + LoRA 的约束版，补齐矩阵。
3. **加成本 + 延迟两列**：$/1k 文档、s/文档，让矩阵变成"精度×成本×延迟×合规"的决策表。
4. **写决策结论**：一张推荐表 + 一段"为什么本地 LoRA 是金融场景对的选择"。

## 5. 重要澄清：这个项目不需要"多场景"才成立

- **选型研究在单域（CORD）上就完整**。多领域 / Orchestrator 是**另一个**（架构可扩展性）主张，是可选的 stretch，不是必须。
- 所以你**不必**为了"多场景"去手搓第二个域的数据——P0 全靠 CORD 现成 gold，你已经做了一半（E0 + E2），剩下 E1/E3/E4 + 成本延迟 + 结论。**你缺的不是数据，是把已设计的对比跑完。**
