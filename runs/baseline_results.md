# CORD 基线结果（E0）

环境：Mac M1 Max · Ollama `qwen3.5:4b`（GGUF Q4, 3.4GB）· test 集 100 条 · `think:false`

## 结果

| 模型/实验 | JSON可解析率 | schema合法率 | micro-F1 | macro-F1 | 最差字段 | 延迟 |
|---|---|---|---|---|---|---|
| **E0 基座·自由解码** | 96.0% | 26.0% | **0.409** | 0.233 | menu.cnt | 2.17s/样本 |

> E1（基座·约束解码）在 Ollama 上对 qwen3.5 未能生效，见下方说明 → 改到 vLLM/GPU 侧做。

## 关键操作性发现

1. **必须 `think:false`**：Qwen3.5 默认思考模式会在抽取前生成大量推理 token，
   关掉后从 **79s/样本 → 2.17s/样本**（35×）。
2. **schema 合法率仅 26%**：基座把金额输出成**数字**（`price:60`）而非字符串，
   不符合 str 类型 schema。这恰恰说明微调 + 约束解码的价值（会把它拉到接近 100%）。
3. **Ollama 约束解码对 qwen3.5 不可靠**：`format:"json"` 生效（去掉 ```json``` 包裹），
   但 `format:<json schema>` 被忽略（仍生成 `60-5.455+60` 这种非法表达式，证明无语法约束）。
   原因：Ollama/llama.cpp 对该新架构的「schema→GBNF 语法」未接上。
   → **E1/E3 的约束解码改在 vLLM `guided_json`（GPU）上做**，与架构无关、可靠。

## 结论

- E0 基线确立：**micro-F1 ≈ 0.41**，这是 LoRA 要超越的下限。
- Mac/Ollama 适合跑「自由解码」基线与 demo；**约束解码归到 GPU/vLLM 侧**。
- 下一步：Colab 训 LoRA → 回本地跑 E2（自由）→ vLLM 跑 E3（约束）。


## E2 最终结果（LoRA 微调后, test 100 条）

| 模型/实验 | JSON合法率 | micro-F1 | macro-F1 | 最差字段 | 延迟(s) |
|---|---|---|---|---|---|
| E0 基座·自由 | 26.0% | 0.409 | 0.233 | cnt | - |
| E2 LoRA·自由 | 100.0% | 0.950 | 0.955 | menu.nm | - |

- micro-F1 **0.409 → 0.950**；schema 合法率 **26% → 100%**（微调即解决，无需约束解码）
- Recall **0.357 → 0.951**（漏抽问题消除）；macro≈micro（幻影字段消失，字段数 15→9）
- 单卡本地 transformers+peft(MPS) 推理 ~10s/样本（thinking 关闭）

## ⚠️ 数据泄漏核查与修正（重要）

复核 train/test 是否有重叠时发现：**CORD-v2 官方 split 本身**在 train(800)/test(100) 之间存在
**8 条完全相同的原文**（非本项目转换脚本引入的 bug，是上游数据集自带的重复条目）。

| 子集 | 条数 | E2 micro-F1 |
|---|---|---|
| 全部 test | 100 | 0.950 |
| 有泄漏的 8 条（train 中出现过原文，模型"背过"） | 8 | 1.000 |
| **真正干净（无泄漏）的 92 条** | 92 | **0.945** |

**结论**：泄漏影响极小（0.950 → 0.945，仅 -0.005），说明 LoRA 学到的是真实泛化能力而非记忆。
**对外报告以 0.945（92 条干净子集）为准**，更严谨。

**根因与后续动作**：
- 根因：CORD-v2 数据集里存在跨 split 的重复样本（常见于众包/合成小样本数据集）。
- 已加 `shared/dedup_check.py`：任何新数据集接入前，先跑 train/test 精确文本去重核查。
- Phase 2（NDA/发票/CCKS）新数据集会先跑这个核查，避免同样问题。

## Prompt engineering 能救多少？（E0简版 vs E0带字段说明 vs E2，干净92条）

| 实验 | schema合法率 | micro-F1 | macro-F1 | Recall |
|---|---|---|---|---|
| E0 基座·简版 prompt | 26% | 0.390 | 0.227 | 0.340 |
| E0 基座·带字段说明 | 21% | 0.466 | 0.286 | 0.424 |
| E2 LoRA | 100% | 0.945 | 0.949 | 0.946 |

**结论（选型硬证据）**：
- 加字段说明（prompt engineering）确实提升：micro-F1 0.390→0.466（+0.076，recall 明显↑，模型搞清 nm=品名/cnt=数量后少漏抽）。
- 但 **prompt 救不了输出类型契约**：schema 合法率仍 ~20%（基座照样输出数字而非字符串）。
- **微调这根杠杆远强**：+0.076 (prompt) vs +0.555 (微调)；prompt 只填平差距的 ~14%，且只有微调把 schema 拉到 100%。
- → 证明这是"行为/格式"问题：**该微调，不是该堆 prompt**。（脚本：`run_ollama.py --rich`）

## Prompt 完整度阶梯（公平性修正，干净92条）

之前 prompt 只给字段名、没说输出类型，对大模型不公平（schema 合法率被低估）。补全 prompt 后重测基座：

| 实验 | prompt 内容 | schema合法率 | micro-F1 |
|---|---|---|---|
| E0 简版 | 只字段名 | 26% | 0.390 |
| E0 带字段说明 | + 每字段含义 | 21% | 0.466 |
| E0 完整版 | + 字段含义 + 类型要求(值输出字符串) | **47%** | **0.647** |
| E2 LoRA | (简版即可，规矩在权重里) | **100%** | **0.945** |

**结论**：
- schema 合法率确实被 prompt 完整度影响（26%→47%），之前的低分部分是"没说清"的假象。
- 但 prompt 写到最全（0.647 / 47%），基座仍远不及微调（0.945 / 100%）。**这是公平的强证据：给了所有该给的指示，通用模型仍追不上专门微调。**
- 对 E4 影响：API 模型也须用完整 prompt 重跑才公平（`run_api.py --full-prompt`）。之前 DeepSeek/Qwen 用简版，schema 3%/1% 不公平（F1 因归一化仍可比）。

### ⚠️ 方法论局限（如实标注，未消融）

**思考/推理模式未被统一控制**，各模型用的是各自默认设置：
- 单条探测（同一样本，max_tokens=2048）实测：
  - DeepSeek-V4-Pro：output=1760 tok，其中 **reasoning_tokens=1643（93%）**
  - Qwen3.7-Max：output=2033 tok（撞到2048上限），**reasoning_tokens=1894（93%）**
  - Claude-Sonnet-5：output=112 tok，reasoning_tokens=None（未启用扩展思考）
  - Gemini-3.5-Flash：output=150 tok，reasoning_tokens=0
  - Kimi-K2.6：批跑延迟 273.81s/条 远超其余模型，行为上明显也在做隐藏推理
- **影响**：DeepSeek/Qwen/Kimi 的延迟数字主要反映"默认开着思考"，不是纯推理服务速度；
  这也让它们和 Claude/Gemini 的延迟对比不完全公平（思考默认开 vs 关）。
- **精度未必受损**：正式批跑（max_tokens=4096）三者 schema 合法率仍 100%，未出现截断导致的解析失败，
  说明推理没有实际损伤这次的输出质量，但确实拉长了延迟且存在截断风险（Qwen 在 2048 上限探测中已逼近边界）。
- **未做的消融**：给 DeepSeek/Qwen 关闭思考（如 `enable_thinking=False`）重测速度与精度，本轮未执行，留作后续。

## 决策结论

**在 CORD 收据抽取这一具体的 to-B 文档抽取任务上：**

1. **精度**：微调后的本地 4B LoRA（**0.945**）超过全部 5 个前沿/国产大模型 API（最高 Gemini 0.866），领先 8–16 个点。原因是 LoRA 从 800 条学到了数据集的领域抽取习惯，而通用大模型即便给了完整 prompt 也不知道这些约定。
2. **成本**：本地 **$0 边际成本**（一次性训练+硬件）；API 按 token 计费、随量线性增长，且思考型国产模型（DeepSeek/Qwen/Kimi）因推理 token 使成本再放大 5–6 倍。
3. **合规**：金融/政务场景数据**不能出境**——本地可私有化部署，闭源 API（GPT/Claude/Gemini）做不到，这是硬红线。
4. **延迟**：当前本地数字未优化，不是本地的优势项；生产需用 vLLM 才公平。

**→ 对数据不能出域的金融文档抽取，微调的本地小模型在精度、成本、合规三个硬轴上全面胜出，是正确选择。**

**方法论诚实度**（面试加分）：全程控制了变量（同测试集/同评测器/同完整prompt/去数据泄漏92条），并如实标注了未消融的局限（思考模式默认设置不统一、本地延迟未优化）——不藏、不吹。
