# 模型选型完整评测报告：通用大模型 API vs 本地微调小模型

> 一个 to-B 文档抽取的选型问题：客户数据不能出内网，该买通用大模型 API，还是在本地微调一个小模型？
> 这份报告把它做成三轮可测的实验——**API 裸跑 → API 补足示例 → 本地微调**——并给出成本测算与诚实的局限标注。

**实验日期**：2026-07 · **评测器**：`shared/eval.py`（字段级 micro-F1）· **原始数据**：`runs/`

---

## 0 口径（先说清楚，否则后面的数字没有意义）

| 项 | 设定 |
|---|---|
| 主对照数据集 | CORD-v2 收据抽取，**干净 92 条**（官方 split 自带 8 条跨 split 重复，一律剔除） |
| 去泄漏方式 | `shared/eval.py --exclude-leaked-from data/cord/train.eval.jsonl`（代码内固化，可复现） |
| prompt | 所有参与方**用同一个完整 prompt**（含字段说明 + "值一律输出字符串"的类型要求） |
| 温度 | 0（Kimi 系列强制为 1，是模型限制） |
| API 通道 | GMI Cloud 聚合平台 |

**报告的五类指标**：

| 指标 | 含义 | 怎么算 |
|---|---|---|
| **Precision** | 抽出来的有多少是对的（低 = 多抽/幻觉） | TP/(TP+FP) |
| **Recall** | 该抽的抽到了多少（低 = 漏抽） | TP/(TP+FN) |
| **micro-F1** | 整体，按字段实例加权（高频字段主导） | 全部 TP/FP/FN 汇总后算一次 |
| **macro-F1** | 字段均衡性，每个字段一票 | 各字段先算 F1 再平均 |
| **schema 合法率** | 输出形状是否守契约 | Pydantic 校验通过率 |

单位是 **(字段路径, 归一化值) 的多重集**：JSON 拍平成叶子对，丢弃 null，列表不带下标（顺序无关），
归一化后做多重集比对得到 TP/FP/FN。**micro 与 macro 必须一起看**——本轮就抓到一个实例，见 §2.5。

> 📐 **这五个指标具体怎么算，见[附录 A](#附录-a-五个指标怎么算用真实样本逐步演算)**——
> 用真实样本从拍平、比对到套公式逐步演算了一遍，包括 P 和 R 的分母为什么不同、
> schema 合法率与 F1 为什么是互补而非重叠的两个维度。

延迟见 §5，成本见 §6。

**为什么强调 prompt 同口径**：抽取任务里，"没说清楚"和"做不到"是两回事。给基座只给字段名时 CORD 只有 0.390，
补上字段含义到 0.466，再补上类型要求到 0.647——**光是把话说全就涨了 0.257**。
所以任何对照都必须建立在"该说的都说了"之上，否则测的是提示词质量而不是模型能力。

## 1 第一轮：API 裸跑（零示例）

六个前沿/国产旗舰模型，完整 prompt，不给任何示例。

**数据集：CORD 干净 92 条**——第 1、2 两轮（API 相关）全部只在 CORD 上做，
第 3 轮（本地微调）才是三个域。跨域结论只能引用 §3.2。

| 模型 | 厂商 | Precision | Recall | micro-F1 | macro-F1 | schema |
|---|---|---|---|---|---|---|
| Qwen3.7-Max | 阿里 | 0.819 | 0.906 | **0.860** | 0.902 | 100% |
| Gemini-3.5-Flash | 谷歌 | 0.833 | 0.871 | 0.852 | 0.904 | 99% |
| MiniMax-M3 | MiniMax | 0.795 | 0.905 | 0.846 | 0.861 | 99% |
| GLM-5.2 | 智谱 | 0.833 | 0.844 | 0.838 | 0.880 | 95% |
| Kimi-K3 | 月之暗面 | 0.816 | 0.859 | 0.837 | 0.882 | 98% |
| DeepSeek-V4-Pro | 深度求索 | 0.791 | 0.861 | 0.824 | 0.843 | 98% |
| — | | | | | | |
| 本地基座 Qwen3.5-4B（同 prompt，未微调） | | 0.694 | 0.606 | 0.647 | 0.491 | 47% |

**读数**：

1. 六个旗舰挤在 **0.824~0.860** 这个很窄的区间里，彼此差距（3.6pp）不到后面会看到的重跑波动（±1.4pp）的三倍。
   换句话说，**在这个任务上换厂商基本没有意义**。
2. **API 普遍是 Recall > Precision**（多数模型 R 比 P 高 4~11 个点）——说明它们倾向于**多抽**：
   该抽的基本都抓到了，但也抓了不少不该抽的。这与后面 few-shot 主要提升 Precision（§2.4）是同一件事的两面。
3. 本地 4B 基座 0.647，比任何 API 低 18~21 个点——参数量差距在零样本条件下是真实存在的。
   而且它是唯一一个 **P > R** 的（0.694 vs 0.606），方向相反：不是多抽，是**大量漏抽**。
4. schema 合法率上，本地基座只有 47%，问题几乎全在"金额输出成数字而非字符串"。
   API 侧 95~100%，说明大模型对"照着 schema 输出"这件事本身没有困难。
5. 本地基座 macro-F1（0.491）远低于 micro（0.647），差 15.6 个点——说明它的错误**集中在部分字段上**，
   分布很不均衡；API 侧 micro/macro 差距普遍在 3~5 个点，相对均衡。

## 2 第二轮：给 API 补足示例（few-shot）

### 2.1 为什么必须做这一轮

第一轮的对照**不公平**：后面要对比的本地微调模型见过 800 条标注，而 API 一条示例都没给。
不补上这一轮，"本地微调更强"这个结论就是拿见过题的和没见过题的比。

示例取自 CORD 训练集**固定前 N 条**（不随机，可复现），拼成 `user/assistant` 交替的 in-context 格式。
脚本内置污染核查——实测在 64-shot 档拦下一次：训练集第 44 条正好是那 8 条泄漏样本之一，
不检查就等于把测试题当示例喂进去。

### 2.2 完整梯度（跑满 0/4/8/16/32/64 六档的两个模型）

| shots | Gemini-3.5-Flash | MiniMax-M3 |
|---|---|---|
| 0 | 0.852 | 0.846 |
| 4 | 0.877 | 0.858 |
| 8 | 0.892 | 0.877 |
| 16 | 0.907 | 0.909 |
| 32 | **0.927** | 0.906 |
| 64 | **0.927** | 0.922 |

**Gemini 在 32→64 档完全持平（0.927 → 0.927），确认饱和。** MiniMax 在 16 档后进入 0.906~0.922 的
噪声带。两条曲线都说明：few-shot 的收益有天花板，不是无限逼近。

### 2.3 16-shot 横向对比（六个模型）

| 模型 | F1 (0→16) | 提升 | P (0→16) | R (0→16) | macro (0→16) | schema |
|---|---|---|---|---|---|---|
| Kimi-K3 | 0.837 → **0.915** | **+0.078** | 0.816 → 0.887 | 0.859 → 0.944 | 0.882 → 0.940 | 98%→100% |
| GLM-5.2 | 0.838 → 0.908 | +0.070 | 0.833 → 0.883 | 0.844 → 0.935 | 0.880 → 0.917 | 95%→97% |
| MiniMax-M3 | 0.846 → 0.909 | +0.063 | 0.795 → 0.890 | 0.905 → 0.929 | 0.861 → 0.939 | 99%→100% |
| Gemini-3.5-Flash | 0.852 → 0.907 | +0.055 | 0.833 → 0.874 | 0.871 → 0.943 | 0.904 → 0.936 | 99%→100% |
| Qwen3.7-Max | 0.860 → 0.903 | +0.043 | 0.819 → 0.866 | 0.906 → 0.943 | 0.902 → 0.934 | 100%→100% |
| DeepSeek-V4-Pro | 0.824 → 0.860 | **+0.036** | 0.791 → 0.841 | 0.861 → 0.881 | 0.843 → 0.908 | 98%→99% |

**同样 16 个示例，收益从 +0.036 到 +0.078，差了一倍多。**「给 API 加示例」这条路的收益并不可预期，
它取决于模型本身，做方案时不能当成一个确定的系数。

补一句 schema：**GLM-5.2 是唯一没能靠示例把 schema 合法率拉满的**（95%→97%），
其余五家在 16-shot 时都到了 99~100%。

### 2.4 收益来自哪里：Precision，不是 Recall

以 MiniMax-M3 为例：

| shots | Precision | Recall |
|---|---|---|
| 0 | 0.795 | 0.905 |
| 64 | 0.898 | 0.948 |

**Precision 涨 10.3 个点，Recall 只涨 4.3 个点。** 说明示例教会的是"输出约定"——
什么算一个菜品行项、字段该怎么切——从而少抽错、少幻觉，而不是让模型看见更多本来看不见的东西。
这也解释了为什么会饱和：约定是有限的，讲完就没了。

六个模型都是同一方向：16-shot 相对 0-shot，**Precision 平均涨 5.9 个点，Recall 平均涨 5.9 个点**，
但起点不同——0-shot 时普遍 R > P（多抽），补上示例后两者收敛到接近。

### 2.5 一个必须同时看 micro 和 macro 的实例

MiniMax-M3 在 32-shot 档出现了一次结构性错误：

| shots | micro-F1 | macro-F1 | 输出字段数 |
|---|---|---|---|
| 16 | 0.909 | 0.939 | 9 |
| **32** | **0.906** | **0.705** | **12** |
| 64 | 0.922 | 0.946 | 9 |

32-shot 时它把 `menu.price` 输出成了**嵌套对象**（里面又套 `{nm, cnt, price}`），5 条文档如此，
凭空造出 3 个 F1=0 的"幻影字段"。**micro 几乎没动（0.909→0.906），macro 却塌了 23 个点。**

因为 micro 按字段实例加权，5 条文档的错误淹没在几百个正确实例里；而 macro 每个字段一票，
三个 0 分字段直接把平均拉下来。**只报 micro 会完全错过这次结构性退化。**

## 3 第三轮：本地微调（LoRA）

### 3.1 配方

| 项 | 设定 |
|---|---|
| 基座 | Qwen3.5-4B（三个域共享同一个，全程不换） |
| 方法 | LoRA，r=16 / alpha=32 / dropout=0.05 / target_modules = 全部 linear |
| 训练 | GCE L4 GPU · bf16 · AdamW-8bit · 3 epochs |
| 耗时 | DuEE-fin 64 分钟（339 步）· CCKS-fraud 1 小时 42 分（567 步） |

### 3.2 三域结果（统一用完整 prompt 基线）

| 域 | 语言 / 任务 | n | 配置 | Precision | Recall | micro-F1 | macro-F1 | schema |
|---|---|---|---|---|---|---|---|---|
| CORD | 英文 / 收据字段抽取 | 92 | 基座 | 0.694 | 0.606 | 0.647 | 0.491 | 47% |
| | | | **LoRA** | **0.944** | **0.946** | **0.945** | 0.949 | **100%** |
| DuEE-fin | 中文 / 金融公告事件抽取 | 227 | 基座 | 0.347 | 0.300 | 0.322 | 0.303 | 88% |
| | | | **LoRA** | **0.862** | **0.860** | **0.861** | 0.796 | **100%** |
| CCKS-fraud | 中文 / 反欺诈案例要素抽取 | 386 | 基座 | 0.180 | 0.293 | 0.223 | 0.233 | 100% |
| | | | **LoRA** | **0.727** | **0.701** | **0.714** | 0.637 | **100%** |

**提升**：CORD +0.298 · DuEE-fin +0.539 · CCKS-fraud +0.491（micro-F1），schema 合法率全部拉到 100%。

一个跨三域一致的现象：**微调后 P 与 R 几乎相等**（0.944/0.946、0.862/0.860、0.727/0.701），
而微调前三个域各自偏向不同（CORD 偏 P、CCKS 偏 R）。说明微调不只是把分数抬高，
还把"多抽还是漏抽"这个偏置**校正到了平衡点**——这正是对齐到数据集标注习惯的表现。

> ⚠ **一处口径修正**：早期文档里写过"三域提升稳定在 +0.49~0.54"，那是**混用了两种基线**——
> CORD 用的是简版 prompt 基线（0.409），另外两域用的是完整 prompt 基线。
> 统一到完整 prompt 后，CORD 的提升是 **+0.298 而不是 +0.536**，明显低于另外两域，不是"稳定一致"。
>
> 原因是可解释的：CORD 基座的主要问题是"金额输出成数字"这个**类型错误**，
> 而完整 prompt 里那句"值一律输出字符串"直接修好了大半（0.390→0.647）。
> 另外两域字段天生是中文文本，没有这个类型冲突，所以 prompt 帮不上忙。
> **微调的增益，在 prompt 修不好的地方最大**——这比"三域惊人一致"是个更有信息量的结论。

### 3.3 微调修的到底是什么

以 CORD 为例，基座（完整prompt）→ LoRA：

| | 基座 | LoRA |
|---|---|---|
| schema 合法率 | 47% | 100% |
| Precision | 0.694 | 0.944 |
| Recall | 0.606 | 0.946 |

Recall 从 0.606 涨到 0.946，说明基座**大量漏抽**。这不是知识问题（收据上的字都认识），
是**行为对齐问题**——不知道这个数据集把什么算作一个行项、哪些该填哪些该留空。
这类问题正是微调擅长而 prompt 与 RAG 都解决不了的。

## 4 三轮合起来看（全部为 CORD 单域）

⚠ **这张表只有 CORD 一个域**，不是三域的合并或平均。

原因：**API 对照只在 CORD 上跑过**，DuEE-fin 与 CCKS-fraud 没有对应的 API 数据（见 §8.1），
所以合不进来。因此下表「本地 4B LoRA」那一行与 §3.2 里 CORD 的 LoRA 行**是同一个数**——
不是巧合，就是同一次评测。三域的微调结果请看 §3.2，那张表才是跨域的。

「三轮」指的是三**轮实验**（API 裸跑 → API 补足示例 → 本地微调），不是三个**域**。

| 方案（CORD 干净 92 条） | Precision | Recall | micro-F1 | macro-F1 | schema | 相对本地 LoRA |
|---|---|---|---|---|---|---|
| **本地 4B LoRA**（= §3.2 CORD 行） | **0.944** | **0.946** | **0.945** | 0.949 | 100% | — |
| API 最佳（Gemini-3.5-Flash，32-shot 饱和） | 0.902 | 0.953 | 0.927 | 0.938 | 100% | −0.018 |
| API 次优（Kimi-K3，16-shot） | 0.887 | 0.944 | 0.915 | 0.940 | 100% | −0.030 |
| API 裸跑最佳（Qwen3.7-Max，0-shot） | 0.819 | 0.906 | 0.860 | 0.902 | 100% | −0.085 |
| 本地基座（完整 prompt，未微调） | 0.694 | 0.606 | 0.647 | 0.491 | 47% | −0.298 |

值得注意的是**领先来自 Precision 而非 Recall**：本地 LoRA 的 Recall（0.946）其实略低于
Gemini 32-shot（0.953），赢的是 Precision（0.944 vs 0.902）。
即**微调模型更少抽错，而不是抽得更全**——它学到的是这个数据集"什么不该抽"的边界。

**一句话**：零示例时本地微调领先约 8.5 个点；给 API 补足示例后，差距收敛到 **1.8 个点**。

### ⚠ 这 1.8 个点有多可信：API 有重跑波动

同模型、同 prompt、同 92 条、temperature=0，把三个模型的 0-shot 各重跑一次，**全部与首轮不同**：

| 模型 | 首轮 | 重跑 | 差 |
|---|---|---|---|
| Gemini-3.5-Flash | 0.866 | 0.852 | −1.4pp |
| DeepSeek-V4-Pro | 0.838 | 0.824 | −1.4pp |
| Qwen3.7-Max | 0.854 | 0.860 | +0.6pp |

逐条比对 Gemini 两次输出，**100 条里只有 37 条完全相同**（差异是实质性的，
例如同一张小票的品名一次抽成 `"TICKET CP"`、一次抽成 `"901016 -TICKET CP"`）。

**所以 1.8pp 这个差距只比重跑波动高一点点，诚实的说法是「本地微调与最强 API 打平，微弱领先」，
而不是「精度上碾压」。** 而本地微调模型是确定性推理（temperature=0 + 固定权重），不存在这个波动
——这本身是可控性的一条实证。

## 5 延迟

### 5.1 本地（干净数据：单进程顺序跑，90 条域内文档）

| 域 | n | 路由中位 | 抽取中位 | 端到端中位 | 端到端 p90 |
|---|---|---|---|---|---|
| CORD | 30 | 1.04s | 11.05s | 12.39s | 20.76s |
| DuEE-fin | 30 | 1.50s | 9.72s | 11.25s | 20.54s |
| CCKS-fraud | 30 | 1.51s | 5.02s | 6.54s | 11.06s |
| **全部** | 90 | — | — | **10.35s** | **18.25s** |

路由（零样本判类，复用同一基座）只占端到端的 **10~14%**，是可忽略的开销。

⚠ 这是 **Mac M1 MPS 上 transformers+PEFT 的开发配置**，没有任何生产优化
（无 vLLM、无批处理、无量化、无 KV-cache 复用）。生产部署预期快一个量级，但**本轮未实测**，
所以延迟不作为本次选型的论据。

### 5.2 API（单请求延迟，串行基准）

主实验的 few-shot 矩阵是 9~16 个进程并发打同一个端点跑的，那批耗时含排队与限流，
**不能用于跨模型比较**。这里单独做了一次严格串行的基准：一次只有一个请求在飞，
每配置前 20 条（所有模型看同一批文档）。

| 模型 | 0-shot 中位 | p90 | out tok | 0-shot 吐字速度 | 16-shot 中位 | p90 | out tok |
|---|---|---|---|---|---|---|---|
| MiniMax-M3 | **1.84s** | 3.75s | 140 | 76 tok/s | 2.79s | 4.37s | 100 |
| Gemini-3.5-Flash | 5.07s | 8.14s | 1001 | 197 tok/s | **1.83s** | 2.20s | 119 |
| GLM-5.2 | 7.24s | 15.20s | 918 | 127 tok/s | 9.84s | 18.57s | 1152 |
| DeepSeek-V4-Pro | 9.91s | 24.17s | 743 | 75 tok/s | 11.14s | 24.36s | 576 |
| Kimi-K3 | 13.53s | 19.74s | 387 | 29 tok/s | 6.26s | 7.86s | 115 |
| Qwen3.7-Max | 18.12s | 30.25s | 1089 | 60 tok/s | 19.11s | 29.85s | 945 |

**读数**：

1. **单请求延迟差一个数量级**（1.84s ~ 18.12s）。这个差距比精度差距（0.824~0.860，3.6pp）
   大得多——**在这个任务上，选型的真实差异在延迟和成本上，不在精度上**。
2. **慢的原因是输出量，不是服务慢**。Qwen 0-shot 吐 1,089 tok（在写推理过程），
   而 MiniMax 只吐 140 tok。看吐字速度（tok/s），Gemini 反而是最快的（197 tok/s）。
   国产模型多默认开启思考模式，这既拉长延迟也放大 output 成本。
3. **few-shot 对延迟的影响取决于它压不压得住输出**：
   Gemini 从 5.07s → **1.83s**（快 2.8 倍，因为 output 从 1001 → 119 tok），
   Kimi 从 13.53s → 6.26s；而 GLM 和 Qwen 几乎没变——它们即使给了 16 个示例仍在输出上千 token。
4. p90 与中位的比值在 1.5~2.4 之间，**DeepSeek 和 Qwen 的尾部最重**（p90 是中位的 2.4/1.7 倍），
   对有 SLA 要求的场景这一项比均值更要紧。

### 5.3 本地 vs API：可比口径的延迟

上表 API 只做抽取；本地的 10.35s 端到端**含路由**。拉齐口径后：

| | 中位延迟 | 说明 |
|---|---|---|
| 本地 4B LoRA（仅抽取） | 8.75s | Mac M1 MPS，无任何生产优化 |
| 本地 4B LoRA（端到端含路由） | 10.35s | 路由占 1.0~1.5s |
| API 最快（Gemini 16-shot） | **1.83s** | 云端 GPU 集群 |
| API 最慢（Qwen3.7-Max 16-shot） | 19.11s | 思考模式 |

**当前配置下本地不占延迟优势**——比一半的 API 慢。但这是 Mac 笔记本上的开发配置，
与云端 GPU 集群不是同一个量级的硬件，**这个对比本身不公平，不应作为选型论据**。
公平的做法是把本地模型部署到 vLLM + 同级 GPU 再比，本轮未做。

### 5.4 本节的测量偏差（如实标注）

- 串行基准取每配置**前 20 条**，这 20 条比全量 100 条**短约 10%**（中位 104 vs 116 字）。
  但延迟主要由 output token 决定（见读数 2），输入短 10% 的影响很小。
- 20 条样本量下，中位数稳健但 p90 只由 2 条决定，**尾部数字仅供参考**。
- API 延迟含网络往返，测量点在国内网络环境下的 Mac 上，含跨境链路。

## 6 成本测算

单价用**各厂商官方挂牌价**（2026-07 查）。每千条 CORD 文档，含实测的 input/output token：

| 模型 | 配置 | 每千条·无缓存 | 每千条·前缀命中缓存 | vs 自身裸跑 |
|---|---|---|---|---|
| MiniMax-M3 | 0-shot | $0.27 | — | 1.00× |
| MiniMax-M3 | 16-shot | $1.43 | $0.49 | 5.25× |
| DeepSeek-V4-Pro | 0-shot | $0.82 | — | 1.00× |
| DeepSeek-V4-Pro | 16-shot | $2.50 | $0.79 | 3.06× |
| Gemini-3.5-Flash | 0-shot | $10.82 | — | 1.00× |
| Gemini-3.5-Flash | 16-shot | **$8.73** | $2.47 | **0.81×** |
| Gemini-3.5-Flash | 32-shot（饱和点） | $13.57 | $2.80 | 1.25× |
| Kimi-K3 | 16-shot | $16.01 | $4.23 | 1.59× |
| **本地 4B LoRA** | — | **$0（边际）** | — | — |

### 6.1 一个反直觉的发现：few-shot 未必更贵

few-shot 把 input token 推高了 15~45 倍，但**同时把 output token 大幅压低**——
Gemini 裸跑时输出 1,149 tok/条（在写解释和思考），16-shot 后只剩 143 tok（直接吐 JSON）。
而 output 单价是 input 的 6 倍。两相抵消后，**Gemini 16-shot 反而比裸跑便宜（$8.73 vs $10.82）**。

再叠加 prompt 缓存——few-shot 的示例前缀在所有调用间完全相同，是理想的缓存对象，
各家缓存命中价约为正常价的 1/10——**32-shot 缓存后只要 $2.80/千条，是裸跑的四分之一**。

所以「给 API 加示例很贵」这个直觉是错的。**这一轮实验推翻了自己的成本假设。**

### 6.2 本地侧的成本结构

本地不是"免费"，是**成本结构不同**：

| | API | 本地微调 |
|---|---|---|
| 前期投入 | 0 | 标注数据 + 训练（L4 GPU 1~2 小时/域）+ 硬件 |
| 边际成本 | 按 token，随调用量线性增长 | ≈0 |
| 加一个新域 | 改提示词（几乎零成本） | 重走标注+训练（真正的时间在标注上，不在训练） |

**所以存在一个盈亏平衡的调用量**：低于它 API 更划算，高于它本地开始回本。
这条线由三项决定——API 单条单价、本地固定成本的月摊销、每加一个域的一次性投入。
按 §6 表，若选 MiniMax-M3 这类低价模型（缓存后 $0.49/千条），平衡点会相当高；
若选 Kimi-K3（$4.23/千条），平衡点则低得多。**做方案时应该先算这条线，再谈技术选型。**

## 7 结论

### 7.1 精度

**在 CORD 收据抽取上**，微调后的本地 4B 模型（0.945）与最强 API 在补足示例后的水平（0.927）
基本打平，微弱领先 1.8 个点，且这个差距只略高于 API 自身的重跑波动（±1.4pp）。

用一个 4B 的小模型、在单卡 GPU 上训练一两个小时，追平并略微超过参数量高出两三个数量级的前沿旗舰
——这是本次实验最实在的结论。但**它的适用范围要说清楚**：

- 前提是**封闭域的、有标注数据的结构化抽取**任务；
- 且这个对比**只在 CORD 一个域上验证过**。另外两个域（DuEE-fin 0.861、CCKS-fraud 0.714）
  只有微调前后的对比，没有 API 对照，所以**不能说"本地微调在三个域上都追平了 API"**。

### 7.2 但精度打平不等于选型打平

六个旗舰在精度上挤在 3.6pp 的窄带里，本地微调也只领先最强 API 1.8pp
——**精度这个维度上，所有可选项都差不多**。真正拉开差距的是另外四条：

1. **合规**——数据不能出内网时，这不是成本项而是**可行性开关**。有这条约束，可选项只剩本地部署或
   私有化 API，成本比较的意义只在于本地方案自己的规模选择。这一层必须和成本分开讲，
   混在一起就会把一个合规问题错误地降级成价格问题。
2. **延迟**——API 之间差**一个数量级**（1.83s ~ 19.11s，见 §5.2），远大于精度差距。
   而且慢的原因是各家默认开着思考模式在吐上千 token，不是服务慢。
   选型时这一项比精度更值得看。
3. **成本结构**——不是"更便宜"，是"不随调用量增长"。API 之间也差一个数量级
   （缓存后 $0.49 ~ $6.25/千条），存在明确的盈亏平衡点（见 §6.2）。
4. **确定性与可控性**——API 同配置重跑 100 条只有 37 条输出一致；本地固定权重推理是确定的。
   对需要审计、需要复现、需要版本回滚的 to-B 场景，这一条的分量往往超过那 1.8 个点。

**一个反直觉的推论**：如果合规上允许出域，那么"选哪家 API"这个问题的答案，
基本不取决于精度（都差不多），而取决于延迟和成本——按本轮实测，
**MiniMax-M3 在延迟（1.84s）和成本（$0.27/千条）上同时是最优的，精度只比最强的低 1.4pp**。

### 7.3 这轮实验推翻的自己的两个假设

方法论上值得单独记一笔的是，这轮实验**推翻了两个原本写在结论里的说法**：

1. 原以为"本地微调在精度上碾压 API 8~16 个点"——那是**零示例对照造成的假象**，补足示例后只剩 1.8 个点。
2. 原以为"few-shot 的代价是成本大幅上升"——实测**output token 的下降抵消了 input 的上升**，
   Gemini 16-shot 反而比裸跑便宜。

一个对照实验如果只会印证预设结论，那它多半设计得不够严。

## 8 已知局限（如实标注，未消融）

1. **API 对照只在 CORD 一个域上做**。三域微调结果都有，但 API 对照没有在 DuEE-fin / CCKS 上重跑，
   所以"本地微调追平 API"这个结论严格说只在英文收据抽取这一个任务上被验证过。
2. **32/64 档只跑了 Gemini 和 MiniMax**。国产模型多为思考模式（Qwen 实测 22s/条），跑满六档要数小时。
   两条完整曲线都显示 16~32 档饱和，但"别家也会饱和"是**外推不是实测**。
3. **重跑波动只在 0-shot 档测了**。若要给"±1.4pp 波动"更强的支撑，应在某个 few-shot 档也重跑一次。
4. **思考模式未统一控制**。各模型用各自默认设置，国产模型多默认开启推理
   （实测 Qwen 0-shot 单条输出 1,089 tok、GLM 918 tok，而 MiniMax 只有 140 tok）。
   这既拉长它们的延迟也放大 output 成本。关闭思考重测本轮未做——
   **所以延迟表反映的是"各家默认配置下的开箱体验"，不是"服务本身的速度上限"**。
5. **定价是厂商官方挂牌价，实验实际走 GMI 聚合平台**，聚合价可能不同；且大模型价格变动极快
   （DeepSeek 永久降 75%、GLM-5 上调、Qwen 现挂 5 折促销），**成本结论只应看量级、不看小数点**。
6. **本地与 API 的延迟不可直接比较**。本地是 Mac M1 笔记本上 transformers+PEFT 的开发配置
   （无 vLLM、无批处理、无量化），API 是云端 GPU 集群。硬件不在一个量级，
   **§5.3 那张对比表只说明"当前配置下本地不快"，不能推出"本地方案慢"**。
   公平做法是把本地模型部署到 vLLM + 同级 GPU 再比，本轮未做。
7. **延迟基准样本量小**。串行基准每配置 20 条，中位数稳健但 p90 只由 2 条决定，尾部数字仅供参考；
   且这 20 条比全量短约 10%。
8. **历史 Kimi-K2.6 那次 0.785 含 9 条接口超时**（`Request timed out`，非格式问题），
   被当作 F1=0 计入，该数字偏低且不公平，已从本报告主表中移除。

## 附录 A 五个指标怎么算（用真实样本逐步演算）

全部取自 `runs/e0_full.jsonl` / `runs/e2.jsonl` 与 CORD test 集，不是构造的例子。

### A.1 单条文档：从 TP/FP/FN 到 P/R/F1

CORD test 第 0 条，基座（完整 prompt）的输出：

```
INPUT:  901016 -TICKET CP / 2 60.000 60.000 / TOTAL DISC $ -60.000
        TAX 5.455 / Subtotal 60.000 / TOTAL (Qty 2.00 60.000 / EDC CIMB NIAGA No: xx7730 60.000

GOLD:   {"menu":[{"nm":"-TICKET CP","cnt":"2","price":"60.000"}],
         "sub_total":{"subtotal_price":"60.000","tax_price":"5.455"},
         "total":{"total_price":"60.000"}}

PRED:   {"menu":[{"nm":"TICKET CP","cnt":"2","price":"120,000"}],
         "sub_total":{"subtotal_price":"60,000","tax_price":"5,455","service_price":null},
         "total":{"total_price":"60,000","cashprice":"60,000","changeprice":null}}
```

**第一步：拍平 + 归一化。** JSON 展平成 (字段路径, 归一化值) 的多重集，丢弃 null，列表不带下标。
归一化会去掉千分位分隔符——所以 gold 的 `"60.000"` 和 pred 的 `"60,000"` 都变成 `60000`，判为命中。

gold 得到 6 个叶子，pred 得到 7 个（`service_price`/`changeprice` 是 null，丢弃）。

**第二步：多重集比对。**

| 类别 | 具体内容 | 计数 |
|---|---|---|
| **TP**（命中） | `menu.cnt=2`、`subtotal_price=60000`、`tax_price=5455`、`total_price=60000` | **4** |
| **FP**（多抽/抽错） | `menu.nm=ticket cp`、`menu.price=120000`、`total.cashprice=60000` | **3** |
| **FN**（漏抽） | `menu.nm=-ticket cp`、`menu.price=60000` | **2** |

三种错误在这一条里同时出现：

- `menu.nm`：gold 是 `-TICKET CP`，pred 丢了前面的连字符 → **同时进 FP 和 FN**（值替换错）
- `menu.price`：gold `60.000`→`60000`，pred `120,000`→`120000`，把两行金额加起来了 → **同时进 FP 和 FN**
- `total.cashprice`：gold 里根本没有这个字段，pred 凭空抽了一个 → **只进 FP**（纯多抽）

**第三步：套公式。**

```
P  = TP/(TP+FP) = 4/(4+3) = 0.571
R  = TP/(TP+FN) = 4/(4+2) = 0.667
F1 = 2TP/(2TP+FP+FN) = 8/(8+3+2) = 0.615
```

**注意 P 和 R 分母不同**：P 的分母是"你抽了多少"（7 个），R 的分母是"该抽多少"（6 个）。
这一条 R > P，说明它的主要毛病是多抽而不是漏抽。

### A.2 schema 合法率：判形状，不判内容

CORD test 第 2 条，基座输出：

```json
{"menu": [{"nm": "JASMINE MT ( L )", "cnt": 1, "price": "24,000"}, ...]}
```

`json.loads` 完全没问题（**可解析率**这一关过了），但 Pydantic 校验报错：

```
menu.0.cnt
  Input should be a valid string [type=string_type, input_value=1, input_type=int]
```

`cnt` 是整数 `1`，而 schema 要求字符串 `"1"` → **schema 不合法**。

关键在于：**这条记录的内容其实是对的**（数量确实是 1）。schema 合法率只判形状是否守契约，
不判内容对不对。所以它和 P/R/F1 是**互补而非重叠**的两个维度：
- schema 合法但内容全错 → 合法率 100%，F1 很低（这正是域外文档的表现）
- 内容基本对但类型写错 → 合法率低，F1 却不一定差（这就是基座在 CORD 上的情况）

### A.3 micro-F1 vs macro-F1：同一批数据，两种汇总

把 92 条的逐字段统计摊开（基座 vs LoRA）：

| 字段 | 基座 TP/FP/FN | 基座 F1 | LoRA TP/FP/FN | LoRA F1 |
|---|---|---|---|---|
| menu.price | 140 / 36 / 85 | 0.698 | 222 / 7 / 3 | 0.978 |
| menu.nm | 127 / 53 / 103 | 0.620 | 199 / 31 / 31 | 0.865 |
| menu.cnt | 98 / 48 / 102 | 0.566 | 194 / 6 / 6 | 0.970 |
| total.total_price | 64 / 8 / 23 | 0.805 | 85 / 3 / 2 | 0.971 |
| total.cashprice | 49 / 13 / 13 | 0.790 | 56 / 2 / 6 | 0.933 |
| sub_total.subtotal_price | 41 / 31 / 19 | 0.621 | 59 / 3 / 1 | 0.967 |
| total.changeprice | 40 / 3 / 12 | 0.842 | 51 / 1 / 1 | 0.981 |
| sub_total.tax_price | 23 / 10 / 16 | 0.639 | 39 / 1 / 0 | 0.987 |
| sub_total.service_price | 3 / 6 / 7 | 0.316 | 8 / 0 / 2 | 0.889 |
| **`cnt`**（幻影） | 0 / 16 / 0 | **0.000** | — | — |
| **`nm`**（幻影） | 0 / 17 / 0 | **0.000** | — | — |
| **`price`**（幻影） | 0 / 17 / 0 | **0.000** | — | — |

**micro-F1**：所有字段的 TP/FP/FN **先汇总再算一次**。

```
基座:  TP=585  FP=258  FN=380
       micro-P = 585/(585+258) = 0.694
       micro-R = 585/(585+380) = 0.606
       micro-F1 = 2×585/(2×585+258+380) = 0.647

LoRA:  TP=913  FP=54  FN=52
       micro-P = 0.944   micro-R = 0.946   micro-F1 = 0.945
```

**macro-F1**：每个字段**先各算各的 F1，再取平均**（每字段一票，不管它出现 3 次还是 225 次）。

```
基座:  (0.698+0.620+0.566+0.805+0.790+0.621+0.842+0.639+0.316+0+0+0) / 12
       = 5.898 / 12 = 0.491

LoRA:  8.542 / 9 = 0.949
```

**为什么基座 micro(0.647) 比 macro(0.491) 高 15.6 个点**：

那三个 F1=0 的**幻影字段**（`cnt` / `nm` / `price`）是基座把结构拍扁造出来的——
它没有把这些字段嵌套在 `menu` 里，而是直接放在顶层。这些字段 TP=0、FP=16~17，
在 micro 里只贡献 50 个 FP（淹没在 258 个里），但在 macro 里**占了 12 票中的 3 票**，
直接把平均拉低。

去掉这三个幻影字段，基座的 macro 会是 `5.898/9 = 0.655`，与 micro 基本齐平。

**所以两个指标回答的是不同问题**：
- micro 问"总共抽对了多少个值"→ 高频字段主导
- macro 问"是不是每个字段都还行"→ 小字段和幻影字段同等重要

微调后两者收敛到 0.945/0.949，说明**幻影字段消失了、各字段表现也均衡了**——
这是比单看 micro 涨了多少更有信息量的判断。
