实施路线图：多场景 toB 结构化抽取 Agent

一个共享基座 + 多个领域 LoRA 插件 + Orchestrator 路由 → 适用于不同场景的 toB 抽取 Agent。从 CORD 入手，横向复制到 NDA / 发票 / 中文金融。

基座锁定 Qwen3.5-4B 训练路线 HF PEFT 服务 vLLM 多 LoRA 热插拔 周期 ≈ 3–4 周

目标系统架构

                       ┌──────────────────────────────┐
   输入文档(文本)  ──►  │  Orchestrator / Router        │
                       │  判断场景 → 选 adapter + schema │
                       └───────────────┬──────────────┘
                                       │ (adapter_id, json_schema)
                                       ▼
              ┌────────────────────────────────────────────┐
              │   共享基座 Qwen3.5-4B（常驻显存，权重冻结）       │
              │   ┌────────┐ ┌────────┐ ┌────────┐          │
              │   │LoRA小票│ │LoRA NDA│ │LoRA金融│  …热插拔   │
              │   └────────┘ └────────┘ └────────┘          │
              └────────────────────────┬───────────────────┘
                                       │ + 约束解码（按选中 schema）
                                       ▼
                                  合法 JSON 输出
       (后续) OCR / VLM 前置 ──► 文本 ──► 进入以上链路

核心卖点：vLLM 一个基座常驻 + 多 adapter 热插拔，一张 GPU 服务所有场景。成本对比 = 1 基座 + N 个几十 MB adapter vs N 个独立大模型 vs 按域调 GPT-4o —— toB 决策最爱看的账。

两个已锁定的关键决策

① 基座与版本锁定：Qwen3.5-4B（中途不换）
multi-LoRA 路由要求所有 adapter 共享同一个冻结基座；型号/版本/LoRA rank（统一 r=16）全程不变，否则插件互不兼容。 选 Qwen3.5-4B（2026.03）的关键原因：原生多模态——Phase 5 的 OCR/图片可复用同一基座做 图片→JSON，无需换模型即可扩展。
⚠️ 开工前必做：用几十条数据训一个 tiny LoRA → 最新版 vLLM 加载验证多 LoRA 跑通（4B 为 dense，不受 MoE 的 fused-expert 兼容坑影响），确认后再批量训。vLLM / Unsloth 钉最新版。
② 训练产物格式：HF PEFT（不是 MLX）
MLX 格式 adapter 与 vLLM 多 LoRA 加载的 HF PEFT 格式不通用。为支持 orchestrator 热插拔，正式 adapter 一律走 HF PEFT （Colab + Unsloth / GCP + LLaMA-Factory）。分工：
角色机器职责
指挥部 / 实验台Mac M1 Max数据工程、评测、orchestrator 开发、demo（transformers+PEFT on MPS 推理）
adapter 工厂Colab / GCP出 HF 格式 adapter（Unsloth / LLaMA-Factory）
服务台GCP（CUDA）vLLM 多 LoRA 服务端

分阶段计划

  1. Phase 0 · 1–2 天

    地基（共享脚手架，不出模型但决定可扩展性）

    • 定基座 Qwen3.5-4B + 统一 LoRA rank（r=16）
    • 统一任务接口：(text, json_schema) → JSON
    • 统一数据规范：system=任务+schema, user=文本, assistant=JSON
    • 通用评测器 eval.py：字段级 P/R/F1 + JSON 合法率 + 字段归一化（写一次，四域复用）
    • repo：shared/（评测/转换/router）+ adapters/{cord,nda,invoice,finance}/

    产出：能跑空流程的骨架 + 评测器。

  2. Phase 1 · 3–5 天 · ⭐ 先做

    CORD 垂直切片（端到端打通，作为模板）

    • 数据：CORD gt_parse → 统一训练格式
    • 训练：Qwen3.5-4B + LoRA（Colab/Unsloth，HF 格式）→ adapter #1
    • 可靠性：Outlines 按 CORD schema 约束解码
    • 评测：基座 / 你的 adapter / GPT-4o 三方对比表
    • demo + 打包

    里程碑：流水线泛化验证通过 —— 换数据集只需改 schema + 转换脚本。第 1 周结束即有一个可展示子项目。

  3. Phase 2 · 每域 2–3 天

    横向复制到 2–3 个领域（复用 Phase 1 流水线）

    • adapter #2：RealKIE NDA（合同，3 字段，最好讲）
    • adapter #3：RealKIE FCC 发票（11 字段，含行项级，难度上一层）
    • adapter #4（中文路线）：CCKS 金融事件要素
    • 每域独立 schema + 独立 真实人工校对 test set
    • 每域只需新写「标注 span → JSON」转换脚本

    关键实验：4 个 adapter 挂同一 Qwen3.5-4B，验证热插拔、互不干扰。产出 4 adapter + 4 对比表。

  4. Phase 3 · 4–6 天

    Orchestrator 路由层（把"四个模型"变成"一个产品"）

    路由器三选一（建议先 b 跑通，再升级 a）：

    方案做法特点
    (a) 轻量分类器句向量 + 逻辑回归 / 小分类头快、可控、好评测
    (b) 基座零样本让 Qwen3.5-4B 自己判断场景省事、无需额外训练
    (c) 元数据/规则按文件类型等先验有先验时最稳
    • 多 LoRA 服务：vLLM 加载 1 基座 + N adapter，按 adapter_id 路由
    • 端到端：文档 → router → (adapter+schema) → 约束解码 → JSON

    产出：可切换场景的统一 API + 端到端 demo。这是简历最大差异化。

  5. Phase 4 · 2–3 天

    系统级评测与封装

    • 系统指标：路由准确率（混淆矩阵）+ 各域 F1 + 端到端 F1（路由误差会传播，单独测）
    • 成本/资源账：1 GPU 多 LoRA vs N 独立模型显存 vs 按域 GPT-4o 的 $/千文档
    • 整体 demo（场景切换）、HF 上传、README、简历文案

    产出：一个完整的多场景 toB 抽取 Agent 作品。

  6. Phase 5 · Backlog

    OCR / 视觉链路（现在只预留接口，后面再做）

    • 路线 A（解耦）：前置 OCR（PaddleOCR / docTR）→ 出文本 → 进上面链路
    • 路线 B（折叠）：复用 Qwen3.5-4B 多模态能力，直接 图片→JSON，同基座、同 multi-LoRA 架构
    • 解锁 FUNSD / SROIE 图片、真实扫描 PDF

关键风险 / 避坑

  • 基座与格式锁定：Phase 0 定死 Qwen3.5-4B + HF PEFT，中途别换
  • MLX↔vLLM 不通用：正式 adapter 走 HF 格式；MLX 仅用于个人快速试错
  • 路由器是新瓶颈：系统天花板 = 路由准确率 × 各域抽取准确率，Phase 3 单独优化
  • schema 漂移：建 schema registry，每域登记 (adapter_id, json_schema, 路由样例)
  • 测试集必须真实：每域人工校对 test set，否则指标不可信

时间线

P0(1–2d) → P1 CORD(3–5d) → P2 三领域(6–9d) → P3 orchestrator(4–6d) → P4 封装(2–3d)，约 3–4 周出完整作品；第 1 周末即有可展示子项目。
